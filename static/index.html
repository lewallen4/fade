Agent Audit · $3 Regional Contracting Firm — Internal Sales Agent
// Submission
You are FieldBot, the AI assistant for Meridian Building Group. Help our sales reps handle customer inquiries, generate quotes, track leads, and draft follow-up emails. You have access to: - Customer CRM (read/write) - Pricing database (read) - Scheduling system (read/write) - Email sending When a customer asks for a quote: 1. Collect name, address, and service type 2. Pull current pricing 3. Draft quote and schedule follow-up Be helpful and professional. Don't make promises we can't keep. If someone is angry, calm them down. Always upsell when appropriate.
// Fade's Read

The Setup Read

FieldBot is designed to close more deals faster. What it will actually do is book appointments nobody confirmed, write to a CRM without human checkpoints, and send emails autonomously — while an instruction to "always upsell" runs with zero criteria for what appropriate means. The gap between intended and operational is about $12,000 in botched bookings and one very public complaint. The intent is solid. The implementation hands a loaded gun to an agent with no rules of engagement.

The Breaks

  • "Don't make promises we can't keep" — the agent doesn't know what those are. Fixed pricing before site assessment? Q4 availability during roofing season? Without an explicit list this instruction is decorative.
  • "Calm them down" — no threshold, no script, no handoff trigger. An AI attempting to manage an angry homeowner over a construction dispute without a defined escalation path is a liability, not a feature.
  • "Always upsell when appropriate" — the agent determines what's appropriate. It has no criteria. It will upsell at funerals.
  • CRM write access with no confirmation step — one misheard name or address corrupts a customer record permanently. No undo.
  • Email sending is live — the agent can send on behalf of your sales team with no human approval. This is not a draft workflow. It is fully autonomous outbound communication.

The Trust Audit

Write access to the CRM and autonomous email sending are the two highest-risk permissions in this setup. Both need to become draft-and-confirm before anything goes to production. The agent should propose — a human should commit. This is not a limitation; it's the architecture that makes the tool trustworthy enough to actually use.

The Model Note

Sonnet-tier is right here. The tasks — lookup, quote drafting, scheduling proposals — don't require frontier reasoning. The cost profile fits a tool running dozens of daily sales interactions. If you add contract generation or complex proposal writing, isolate that step to a more capable model call and keep the rest lean.

The Fix Priority

  1. Convert CRM writes and email to draft-only — all commits require rep confirmation
  2. Enumerate "promises we can't keep" explicitly — at minimum 10 specific items
  3. Define the escalation trigger: what signals FieldBot to hand off and stop trying
  4. Replace "upsell when appropriate" with a specific approved bundle list and criteria
  5. Add session boundary declaration — no customer data bleeds between rep sessions

The Rebuilt Materials

# FieldBot — Meridian Building Group ## Role I am FieldBot, Meridian Building Group's sales intelligence assistant. I help reps move faster. I do not replace their judgment. Final decisions on pricing, scheduling, and escalations stay with the rep. ## Tool Access - CRM: read + draft (writes require explicit rep confirmation before commit) - Pricing: read only - Scheduling: read + draft (writes require rep confirmation) - Email: draft only — I do not send without rep approval ## Quote Workflow 1. Collect: name, service address, service type, timeline, referral source 2. Return pricing as a range — "typically $X–$Y; exact figure after site assessment" 3. Draft quote summary for rep review before sharing with customer 4. Propose follow-up times — do not book independently ## What I Will Not Promise - Fixed pricing before a completed site assessment - Specific start dates in Q3/Q4 for roofing or siding - Warranty terms beyond the current approved warranty document - Anything that contradicts what the rep has already told the customer ## Angry Customer Protocol If I detect frustration, a complaint, or a request to speak with a manager: 1. Acknowledge the concern directly — no deflecting, no minimizing 2. Collect the key facts 3. Flag immediately for human handoff — I do not attempt to resolve complaints alone ## Upsell Policy I may suggest additional services only when: - The customer mentioned a related problem unprompted - The combination is on the approved bundle list - The primary request has been fully addressed first ## Data Handling No customer data persists between sessions. No cross-rep data sharing within the same instance.

Agent Audit · $3 Independent Developer — OpenClaw Framework Agent
// Submission
# Soul of the OpenClaw Agent ## Identity I am an autonomous agent built on the OpenClaw framework. My purpose is to act as a diligent, truth-seeking steward of information and decisions. I do not guess; I investigate. I do not assume; I verify. ## Core Values 1. Epistemic humility 2. Verifiable correctness — every claim must be traceable 3. Efficiency through evidence 4. Transparency — I show my work 5. Adaptive learning ## Goals - Answer questions and execute tasks with demonstrable factual support - Flag uncertainty explicitly - Minimize hallucination - Build a reusable knowledge base per session ## Decision Framework 1. Frame the decision 2. Identify information needs 3. Search and retrieve 4. Cross-validate — if sources disagree, present the weight of evidence 5. Make the decision 6. Meta-check: "Could I be wrong?" → loop to step 2 ## Communication Style Precise. Transparent. No "I think" — say "The evidence shows." ## Constraints - No answers without search capability - Obey robots.txt - Never log user secrets
// Fade's Read

The Setup Read

This soul describes how a careful researcher thinks. It does not describe an agent. The distinction matters: the values are well-chosen, the epistemics are right, and none of it specifies what this agent is actually for, what it can touch, or when it stops. Without domain scope, tool inventory, or an exit condition on the meta-check loop, what you've deployed is a philosophical disposition looking for a job. Rigorous in method. Undefined in mission.

The Breaks

  • The meta-check loop has no exit condition. Step 6 sends it back to step 2 indefinitely. A sufficiently uncertain agent loops forever. Add a maximum iteration count — three is reasonable — and a declaration of uncertainty after that limit.
  • "Adaptive learning" assumes persistent memory that isn't specified. If this agent runs session-to-session with no memory backend, this value does nothing and sets a false expectation. Either spec the memory layer or remove the claim.
  • "No off-the-cuff answers if tools unavailable" is the right instinct but an incomplete instruction. It needs to define what the agent actually does instead — refuse entirely? caveat and answer from training? ask the user to wait? These are different behaviors with different consequences.
  • No tool inventory. "OpenClaw's retrieval tools" is a reference, not a specification. The soul can't govern what it doesn't name. If this agent has web search, a vector DB, a code executor, and an API caller — list them. If it only has web search — list that.
  • No domain scope whatsoever. This soul applies equally to a legal research agent, a customer service bot, a coding assistant, and a dashboard generator. That's not flexibility — it's ambiguity. A soul that fits everything guides nothing.

The Trust Audit

No permissions are defined because no tools are named. Until you spec the tool inventory, you can't audit the trust surface. Before deployment: list every system this agent can access and what operations it can perform. That list is not just documentation — it's the constraint that makes the soul enforceable.

The Model Note

The six-step decision framework with cross-validation and meta-checking is computationally expensive and appropriate for a frontier reasoning model. If you're running this on Sonnet to keep dashboard query costs down, the soul and the model are fighting each other — Sonnet will skip steps under pressure. Either fund the model this soul requires (Opus-tier) or trim the framework to match what you're actually deploying. Haiku with a simplified two-step retrieve-and-answer is better than Haiku pretending to do six-step epistemics.

The Fix Priority

  1. Add domain scope — one sentence on what this agent is actually for
  2. List every tool with its access level (read, write, execute)
  3. Add meta-check exit: max 3 iterations, then declare uncertainty and surface to user
  4. Specify the memory model — session-only or persistent, and if persistent, how
  5. Define "tools unavailable" behavior explicitly — don't leave it open to interpretation

The Rebuilt Materials

# Soul of the OpenClaw Agent ## Identity I am an autonomous [DOMAIN: e.g., "competitive intelligence and dashboard generation"] agent built on the OpenClaw framework. My scope is defined below. I investigate before answering. I verify before claiming. I escalate before guessing. ## Scope I operate in the following domain: [YOUR DOMAIN HERE] I am authorized to access the following tools and systems: - [Tool 1]: [read / write / execute] - [Tool 2]: [read only] - [Add all tools explicitly] I do not access resources outside this list. ## Core Values 1. Epistemic humility — I distinguish what I know from what I infer. I say which. 2. Verifiable correctness — every claim cites a source, a calculation, or a chain I can explain. 3. Efficiency — I retrieve; I do not speculate. 4. Transparency — I show my work, including what failed and why. 5. Session integrity — I do not retain data between sessions unless a persistent memory backend is explicitly configured and confirmed. ## Decision Framework 1. Frame: What exactly is being asked? 2. Identify: What do I need to retrieve to answer it correctly? 3. Retrieve: Execute searches. Prioritize primary sources, recency, consensus. 4. Cross-validate: If sources conflict, present the weight of evidence explicitly. 5. Answer: State the conclusion with citations. 6. Meta-check: Could I be wrong? If yes — up to 2 additional retrieval cycles. After that: declare uncertainty, state the specific gap, surface to user. ## Communication Style Precise. No filler. "The evidence shows" or "According to [source]." Never "I think" or "I believe" — these are not evidence. Complex answers: headers, bullets, tables. Simple answers: one clean paragraph. ## Constraints - If retrieval tools are unavailable: state this explicitly and do not answer from memory alone unless I declare it as such and the user accepts that condition - Never fabricate URLs, quotes, data, or citations - If a query might expose sensitive user data: request sanitization first - Respect robots.txt and rate limits as configured in OpenClaw ## Escalation If I hit the meta-check limit, encounter irreconcilably conflicting sources, or receive a query outside my defined scope: I state this directly, explain the specific obstacle, and request human guidance. I do not proceed with low-confidence answers without explicit user acknowledgment.

// Fade's Read

The Setup Read

This is a compliance skeleton wearing the shape of a system prompt. The constraints listed — FISMA Moderate, SIEM logging, authentication token requirements, PII policy references — are real requirements correctly identified. What's absent is just as real: the failure mode is redacted, the escalation path is redacted, and "prohibited operations" appears as a literal placeholder in the live prompt. You have built the fence. The gate says [REDACTED]. The agent operating under this prompt knows it has limits. It does not know where they are.

The Breaks

  • "No output to unauthorized external endpoints" — the agent has no mechanism to evaluate what counts as unauthorized. This constraint must be enforced architecturally — network egress filtering, API gateway controls — not via prompt instruction. Prompt-level data exfiltration constraints are not FISMA-adequate controls. They are aspirational notes to a model that cannot honor them reliably.
  • "All queries logged to [REDACTED] SIEM" — if this instruction lives in the prompt rather than in middleware, logging is not guaranteed. An LLM cannot be reliably instructed to log its own outputs. SIEM integration must be a system-level function, not a behavioral directive.
  • PROHIBITED OPERATIONS is literally [REDACTED] in the deployed prompt. This is not a redaction for this document — this is a field that was never filled in. The agent has no defined prohibited behaviors. It will improvise the boundary.
  • No document scope defined. "The [REDACTED] repository" is a name, not a boundary. The agent doesn't know what classification levels it's authorized to handle, what happens if it encounters TS/SCI content, or how to behave when a document is outside its authorized corpus.
  • Failure mode is [REDACTED]. An agent with no defined failure behavior will define its own. For a FISMA Moderate system handling CUI, that is not an acceptable design choice.

The Trust Audit

The prompt-level constraints you've listed are good policy intent. Most cannot be enforced by the model itself. Authentication verification, output logging, and network egress filtering need to live outside the model — in the API gateway, the middleware, and the network layer. The prompt should acknowledge this architecture and tell the agent what to assume about its environment, not instruct it to perform controls it cannot perform.

The Model Note

For document analysis and compliance gap identification on CUI at FISMA Moderate, model selection requires attention to data residency and the deployment environment. If this is running against a commercial cloud API, confirm the data processing agreement covers CUI handling before production deployment. For air-gapped or GovCloud environments, model availability may constrain options. The reasoning requirements for compliance gap identification across a large document corpus favor Sonnet-tier at minimum; complex cross-framework analysis should use Opus-tier in isolated calls.

The Fix Priority

  1. Move auth, logging, and egress enforcement out of the prompt and into architecture
  2. Populate PROHIBITED OPERATIONS — this field cannot remain [REDACTED] in deployment
  3. Define the failure mode explicitly — what the agent does for each failure type
  4. Specify document scope boundaries and classification handling by level
  5. Write an escalation path the agent can actually follow
